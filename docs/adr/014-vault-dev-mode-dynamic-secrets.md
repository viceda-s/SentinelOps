# ADR-014: Vault (dev mode) for dynamic secrets management

**Status:** Accepted

## Context

Every Postgres-backed service (`api`, `webhook-handler`, `worker`, `report-generator`, `maintenance-monitor`) and Grafana read a static credential from `.env`: `RESPONSE_ENGINE_DB_PASSWORD`, `REPORT_GENERATOR_DB_PASSWORD`, `API_DB_PASSWORD`, `GRAFANA_ADMIN_PASSWORD`. These never expired, never rotated, and lived in plaintext in a file checked into every developer's working copy (via `.env.example`).

The least-privilege Postgres roles this design depends on (`response_engine`, `report_generator`) already existed from earlier work; `api` had no such role and connected as the Postgres admin user directly — that gap is closed as part of this migration (see Consequences).

Per ADR-012, Jenkins is this repo's primary CI/CD pipeline; per ADR-013, Jenkins already gained a Node.js runtime for the `release-please` CLI, establishing precedent for `jenkins-agent`'s image gaining tooling beyond its original scope when a dependency requires it.

## Decision

HashiCorp Vault runs as a **dev-mode** service in `docker-compose.yml`: in-memory storage, auto-unseal, reconfigured from scratch by `docker/vault/bootstrap/bootstrap_vault.sh` on every stack bring-up. This is an explicit, accepted trade-off for a single-host Compose dev lab, not a production posture — `automation/scripts/bootstrap.sh` already reconfigures the whole stack idempotently on every run, so Vault losing its state on restart costs nothing this project doesn't already pay elsewhere.

**AppRole auth, one role per service.** `bootstrap_vault.sh` creates an AppRole and a scoped policy per service (`api`, `webhook-handler`, `worker`, `report-generator`, `maintenance-monitor`, `grafana`). Each policy grants read on exactly the one Vault path that service needs — a database credential path, or the Grafana KV secret — never both, and never another service's path.

**Dynamic Postgres credentials via Vault's database secrets engine, one login per lease.** `response_engine`, `report_generator`, and `api` each get a Vault database role whose `creation_statements` runs `CREATE ROLE "{{name}}" ... IN ROLE "<role>"`, not `ALTER ROLE "<role>" ... PASSWORD '{{password}}'`. `worker` and `webhook-handler` both draw leases from the `response_engine` Vault role independently; if creation used `ALTER ROLE` against the fixed role name, one service's lease request would silently invalidate the password the other service was already using against that same physical Postgres role — two services racing to overwrite one shared credential, not isolation. `CREATE ROLE ... IN ROLE` instead gives every lease its own uniquely-named Postgres login that inherits the base role's grants via membership, so concurrent leases never collide. Verified directly: issuing two leases back-to-back produces two different usernames, and the first lease's credential still authenticates after the second is issued (`docker/vault/bootstrap/bootstrap_vault.sh`'s design; verified during Task 4 of the implementation, not just asserted).

`revocation_statements` uses Vault's `REASSIGN OWNED` / `DROP OWNED` / `DROP ROLE IF EXISTS` sequence, not a bare `DROP ROLE`, which Postgres refuses outright if the role still owns objects or holds a live connection. Verified directly: revoking a lease while a connection using it is still open (`pg_sleep(15)` mid-query) succeeds without error, and the role is confirmed gone afterward.

**Vault Agent runs inside each of the 6 affected service images, in `exec` mode, using `env_template` (not `template` + a rendered file).** Vault Agent supervises the real application process directly: authenticates via AppRole, renders each secret straight into the child process's environment via one `env_template` block per variable, launches the real command via `exec`, and — because `exec.restart_on_secret_changes = "always"` — restarts that child with a fresh environment whenever the underlying secret changes (lease renewal, rotation, or expiry). This is Vault Agent's own built-in answer to "how does a long-running process learn its credential changed," not a workaround built on top of it.

**`env_template`, not `template` + `destination`, is a version-driven correction to the original design.** The original plan (written against Vault 1.18-era assumptions) used `template { source = "*.ctmpl", destination = "/vault/secrets/env" }` alongside `exec`, requiring the exec'd process to read that file itself. Vault 2.1.1 (the version this stack actually runs) refuses to start with that combination: `error validating configuration: must specify at least one 'env_template' element with a top-level 'exec' element`. `env_template` sidesteps the problem entirely — Vault Agent injects the rendered value directly into the child's environment, so the four now-unused `.ctmpl` files and the file-read step they implied were deleted rather than kept as dead weight.

**`remove_secret_id_file_after_reading = false` is a required override, not Vault Agent's default-safe behavior left alone.** Vault Agent's AppRole `auto_auth` method deletes `secret_id_file_path` after its first successful read by default — a sensible default for a secret meant to be used once. Combined with `exec.restart_on_secret_changes`, this stack's Vault Agent re-authenticates repeatedly over a container's lifetime (child restarts on every lease rotation), and the default silently broke the second authentication attempt with "no known secret ID" — reproduced directly: first auth succeeds, secret_id file disappears, next auth attempt fails outright. The AppRole `secret_id` already lives inside the built image (see below), so persisting it on disk after the first read doesn't change this design's security posture; it just stops the design from breaking itself.

**`api` gets its own least-privilege Postgres role and Vault database role**, added as part of this migration rather than left as inherited debt: `api`'s Flask app connected as the Postgres admin user (`POSTGRES_USER`/`POSTGRES_PASSWORD`) with no scoped role of its own, discovered while mapping which service needs which Vault database role. A new `api` Postgres role (`SELECT` on `items` only — the only table `api`'s code touches) and a matching Vault database role were added rather than granting Vault-issued admin credentials, which would have "solved" credential rotation while leaving the actual over-privilege in place.

**AppRole `secret_id`s are baked into each image at build time.** `docker/vault/bootstrap/seed_role_ids.sh` fetches each service's `role_id`/`secret_id` into `docker/vault/agent/roleids/<service>/` (gitignored), and each service's Dockerfile `COPY`s its own pair in at build time. This is a deliberate, documented trade-off for a single-host dev lab with no orchestrator-native secret injection: a mounted-volume alternative was considered and rejected, since it reintroduces the shared-volume-plus-external-seeding-script complexity an earlier sidecar-based draft of this design already had. A compromised local image is a rebuild away from invalidated (re-run `seed_role_ids.sh`, rebuild), not a permanent hole; `token_max_ttl=4h` with `secret_id_num_uses` left unlimited lets Vault Agent keep re-authenticating with the same baked-in `secret_id` indefinitely rather than needing a fresh one injected after each forced token expiry.

**Grafana required its own Dockerfile — the project's only vendored image that gains project-authored build steps.** Grafana previously ran `grafana/grafana:11.2.0` directly with `GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_ADMIN_PASSWORD}` set via Compose-file variable interpolation. That interpolation resolves from the host's `.env` at `docker compose up` parse-time, before any container — Vault Agent included — has started; no in-container mechanism can feed a value Compose already substituted before the container exists. `docker/grafana/Dockerfile` builds on the stock image, installs the `vault` binary as `root`, copies in the agent config and baked-in AppRole credentials, then drops back to the image's own non-root user (`472`) before setting `ENTRYPOINT ["vault", "agent", ...]` — Grafana's own `/run.sh` entrypoint (confirmed via `docker inspect`, not assumed) still runs as the user the upstream image expects. Verified directly: `curl -u admin:<vault-issued-password>` against a live container returns `200`; the same call with a wrong password returns `401`.

**Static Postgres constants (`POSTGRES_HOST`/`PORT`/`DB`) still flow through Compose, not Vault.** These aren't secrets, and hardcoding them in each Dockerfile would have broken `.env.test` vs `.env.example` parity (discovered directly: a worker built with `POSTGRES_DB=sentinelops` baked in couldn't reach `sentinelops_test`). A new `POSTGRES_CONTAINER_HOST` env var (always `postgres`, the Compose service's own DNS name) was introduced alongside the existing `POSTGRES_HOST` (which varies — `127.0.0.1`/`localhost` — for the host-side pytest/script use case), since the two need different values inside the Docker network versus on the host, not different values across environments.

## Alternatives considered

- **Vault Agent sidecar + shared volume + `template`-only mode.** The design's original draft. Rejected: `template`-only mode has no way to notify a long-running process that its credential changed once the process has already started — every migrated service would silently keep running on an expired, revoked credential roughly an hour after boot with no verification step ever catching it. Exec mode exists specifically to solve this.
- **`ALTER ROLE` for dynamic credential issuance.** Rejected: creates a credential-overwrite race between any two services sharing a Vault database role (`worker` and `webhook-handler` both draw from `response_engine`), where issuing a new lease silently invalidates the password another service is currently using.
- **Vault-issued admin credentials for `api`, skipping a dedicated Postgres role.** Rejected: rotates the admin credential without addressing the actual over-privilege — `api` would still authenticate as an account that can do far more than `SELECT` on one table.
- **Mounted-volume AppRole credential injection instead of baking `secret_id` into images.** Considered as a way to avoid a secret at rest in a local image layer. Rejected: reintroduces the shared-volume-plus-external-seeding-script complexity this design's move away from the sidecar draft was meant to eliminate, for a security property already covered by this ADR's "dev mode is not a production posture" trade-off.

## Consequences

- No service reads `RESPONSE_ENGINE_DB_PASSWORD`, `REPORT_GENERATOR_DB_PASSWORD`, `API_DB_PASSWORD`, or `GRAFANA_ADMIN_PASSWORD` at runtime anymore; those variables remain in `.env`/`.env.test`/`.env.example` solely as the bootstrap credentials `docker/postgres/init/007_create_roles.sh` and `bootstrap_vault.sh` need to seed the underlying Postgres roles and the Grafana KV secret in the first place — a documented exception, not an oversight.
- `docker/api/Dockerfile`, `docker/webhook-handler/Dockerfile`, `docker/worker/Dockerfile`, `docker/report-generator/Dockerfile`, and `docker/maintenance-monitor/Dockerfile` all install the `vault` binary and run `vault agent -exec=...` as the image's actual entrypoint instead of the application directly; `docker/grafana/Dockerfile` is new.
- `maintenance-monitor` was migrated from `python:3.14-slim` to `python:3.14-alpine` as part of this work, aligning it with every other Python service image in the repo — no dependency required the Debian base, and the inconsistency predated this migration.
- `api`'s Compose service definition and the `Jenkinsfile`'s `Container Build` stage both changed from a `docker/api`-scoped build context to `context: . / dockerfile: docker/api/Dockerfile`, since `docker/api/Dockerfile` now needs to `COPY` files from `docker/vault/agent/`, outside its old build context.
- `docker/vault/agent/roleids/` is gitignored; `docker/vault/bootstrap/seed_role_ids.sh` must be re-run (and affected images rebuilt) any time an AppRole's `secret_id` needs rotating.
- Forcing a short Postgres-role TTL (2 minutes) and waiting past it, on a running `worker` container, showed Vault Agent detecting the secret change, restarting the child process automatically, and the new process holding a different username and password than before — proving live rotation works, not just cold-start credential issuance.
- `ROADMAP.md`'s Post-v1 "Secret management integration" bullet is resolved and removed.
